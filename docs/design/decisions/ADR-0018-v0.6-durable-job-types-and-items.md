# ADR-0018 — v0.6 durable workloads: typed retrieval/content jobs + persistent JobItem checkpoints

**Статус:** accepted

## 1. Контекст

Job framework не должен становиться generic arbitrary task runner.

Для первой Jobs version нужны реальные typed workloads, которые:

- имеют смысл выполнять дольше request-bound deadline;
- можно безопасно продолжить после worker crash;
- дают измеримый progress;
- состоят из независимых элементов;
- не имеют опасных external side effects.

Очевидные кандидаты:

- большой batch HTTP Retrieval;
- большой batch L1 Native Parsing существующих ContentObjects;
- crawl;
- durable browser workflow.

Crawl имеет собственную сложную семантику frontier/robots/dedup/site boundaries и требует отдельного design.

Browser workflow stateful/side-effecting и не должен попадать в generic Job retry.

---

## 2. Решение — первые job types

v0.6 реализует два typed durable job type:

```text
retrieval_batch
content_parse_batch
```

`crawl` не входит v0.6 baseline.

---

## 3. JobItem

Для этих batch job вводится durable child entity:

```text
JobItem
```

Она представляет один логический независимый элемент input batch и сохраняет checkpoint между JobAttempt.

Концептуально:

```text
job_item_id
job_id
item_index
item_type
input_ref/payload
state
attempt_id | null
attempt_count
started_at | null
completed_at | null
result_summary/result_refs
error
next_retry_at | null
revision
```

Input order сохраняется через `item_index`.

---

## 4. Почему JobItem нужен

Без item checkpoint:

```text
256 URL
→ worker успешно получил 200
→ worker crash
→ retry повторяет все 256
```

Это:

- лишний network/storage cost;
- создаёт duplicate ContentObjects;
- ухудшает progress;
- делает cancellation/recovery менее честными.

С JobItem:

```text
200 succeeded
56 pending/running
→ lost JobAttempt
→ new JobAttempt продолжает только eligible 56
```

---

## 5. JobItem states

Baseline:

```text
pending
running
retry_wait
succeeded
failed
cancelled
```

Terminal item states:

```text
succeeded
failed
cancelled
```

Job terminal aggregate определяется после того, как больше нет runnable items.

---

## 6. One active JobAttempt baseline

В v0.6 один Job имеет максимум один active JobAttempt.

Worker внутри attempt может выполнять несколько JobItems параллельно bounded concurrency.

Не делаем distributed item sharding одного Job между множеством workers baseline.

Причины:

- проще cancellation/fencing/progress;
- уже достаточно горизонтального масштабирования по Jobs;
- item sharding можно добавить позже без public contract change.

---

## 7. JobItem claim

После JobAttempt claim worker получает eligible items bounded batches.

Item transition:

```text
pending/retry_wait due
→ running(attempt_id=current)
```

через transaction/CAS.

Только current JobAttempt может завершить `running` item.

---

## 8. Lost attempt recovery

Если JobAttempt lease потерян:

- attempt → `lost`;
- item `running` с этим attempt_id рассматриваются reconciler-ом;
- для safe item type они возвращаются `pending`/`retry_wait` согласно item retry policy;
- already `succeeded` остаются succeeded;
- terminal `failed` остаются terminal, если policy исчерпана.

Старый worker fenced и не может late-commit item result.

---

## 9. `retrieval_batch`

Typed input:

```text
urls[]
common retrieval profile/options allowed by application
```

Каждый URL = один `JobItem` с stable item_index.

Item handler использует тот же SafeHttpFetcher + Content ingest + L0/L1 pipeline, что request-bound `web_fetch`.

Никакой отдельной «job retrieval implementation» бизнес-логики.

---

## 10. Retrieval item semantics

Успешный item сохраняет:

```text
requested_url
final_url
HTTP summary
raw ContentRef
native derived ContentRefs
warnings/hints
retrieved_at
```

Полный item output не обязан помещаться в JobItem JSON row; large/structured final batch manifest хранится как ContentObject.

---

## 11. Retrieval retries

GET Retrieval item относится к safe/read operation, но повтор может получить более новую внешнюю версию страницы.

Policy:

- succeeded item никогда не повторяется в том же Job;
- retry только non-terminal retryable failure/lost running item;
- each retry has new retrieval observation timestamp/provenance;
- previous failed attempt metadata retained bounded;
- no guarantee identical web bytes across attempts.

Это честная web semantics.

---

## 12. `content_parse_batch`

Typed input:

```text
content_ids[]
optional stable requested representation/profile
```

Каждый ContentObject = JobItem.

Handler вызывает тот же `ContentApplication`/NativeParserRegistry, что request-bound `content_parse`.

L2 по-прежнему отсутствует.

---

## 13. Content parse item retries

L1 Native Parsing является deterministic/read-oriented относительно immutable source ContentObject + parser revision/profile.

Поэтому retry lost/transient parser-infrastructure failure безопасен.

Не retry automatically:

- unsupported format;
- parser hard resource limit;
- malformed permanent content;
- encrypted/no-supported-native-content;
- policy/owner rejection.

---

## 14. Representation reuse

Перед новым parse JobItem ContentApplication проверяет existing compatible derived representation по v0.3/v0.5 provenance contract.

Если representation уже существует:

```text
item → succeeded(reused=true)
```

без нового parser subprocess.

Это особенно важно при Job retry/recreation.

---

## 15. Batch limits

Initial MCP durable batch ceilings:

```text
web_fetch execution=durable:
  urls 1..256

content_parse execution=durable:
  content_ids 1..256
```

Request-bound existing limits остаются более узкими.

REST/operator hard ceilings могут быть выше только через explicit configured versioned policy; first implementation hard server ceiling:

```text
max JobItems per public batch Job = 1,000
```

MCP остаётся намеренно уже для LLM context/control.

---

## 16. Total resource budget

Item count alone insufficient.

Initial Job policy содержит server-side aggregate budgets, например:

```text
retrieval_batch:
  default total decoded bytes budget = 512 MiB
  hard ceiling = 2 GiB

content_parse_batch:
  default total source bytes processed = 512 MiB
  hard ceiling = 2 GiB
```

Exact operator default может быть строже.

Budget exhaustion:

- active running items allowed to finish according bounded phase where safe;
- remaining pending items terminal `failed/resource_budget_exhausted` or cancelled-by-policy according job type;
- no hidden ceiling expansion.

---

## 17. Per-item concurrency

Initial per JobAttempt defaults:

```text
retrieval_batch item concurrency = 8
content_parse_batch item concurrency = min(4, parser isolated capacity)
```

Global/provider/per-host/parser limits from underlying components still apply.

Job worker concurrency does not bypass Search/Retrieval/Content admission policies.

---

## 18. Overall Job defaults

Initial public profile:

```text
max attempts per Job = 3
max attempts per item = 3
overall Job lifetime = 6 hours
per JobAttempt execution window = bounded/configurable, default <= 1 hour
```

Retry policies may stop earlier on permanent failures.

Values are configuration under hard server ceilings; MCP caller does not choose infinite retries/lifetime.

---

## 19. Progress

Batch progress is real/measurable:

```text
phase = processing
completed = count(terminal items)
total = item count
unit = items
```

Additional summary:

```text
succeeded
failed
retry_wait/running/pending
bytes processed where meaningful
```

No fake percent beyond actual item completion.

---

## 20. Aggregate Job outcome

When all items terminal:

### All succeeded

```text
Job → succeeded
aggregate outcome = succeeded
```

### Mix succeeded/failed

```text
Job → succeeded
aggregate result status = partial
```

если framework считает Job body корректно завершившим обработку всего batch.

Permanent per-item failures не обязательно делают infrastructure Job `failed`.

### Job framework/system failure

Job → `failed` when:

- handler cannot continue due internal/infrastructure failure after retry policy;
- input manifest corrupt;
- invariant violated;
- overall deadline/budget prevents meaningful completion according policy.

Это разделяет «batch содержит плохие URL» и «сам Job runtime сломан».

---

## 21. Result manifest

Terminal batch Job создаёт immutable structured `ContentObject` manifest.

Conceptual JSON representation:

```text
job_id
job_type
created/completed timestamps
input item count
aggregate status/counts
items[] in original order:
  item_index
  input summary
  outcome
  result ContentRefs/metadata
  error/warnings/hints
```

Если manifest велик, Job row хранит только `result_content_id` + small summary.

`job_get` возвращает summary + manifest ContentRef.

---

## 22. Manifest creation crash

Manifest является ContentObject с ADR-0007 lifecycle.

Job не становится terminal `succeeded` до того, как required result manifest `available`.

Crash между item completion и manifest creation recovered by reconciler/next attempt/finalization phase without rerunning succeeded items.

---

## 23. Cancellation

Cancel Job:

- prevents new item starts;
- cooperative cancels active items;
- completed items remain valid ContentObjects;
- pending items become cancelled;
- running retrieval/parser cancellation follows underlying semantics;
- Job reaches `cancelled` only after no active handler remains.

Partial results may remain accessible in cancelled Job summary/manifest if manifest finalization policy creates one; exact cancellation manifest included v0.6 implementation.

Baseline preference: create final partial manifest for user-visible cancelled batch if at least one item terminal result exists.

---

## 24. MCP facade — one intent remains one tool

Не добавляются:

```text
web_fetch_job
content_parse_job
```

Existing tools получают explicit execution choice:

```text
execution = direct | durable
```

Default:

```text
direct
```

Это **не hidden heuristic**: LLM явно выбирает execution mode.

---

## 25. MCP `web_fetch` cross-field schema

Conceptually:

```text
execution=direct
→ urls 1..8
→ direct bounded result

execution=durable
→ urls 1..256
→ JobRef
```

Actual FastMCP JSON Schema должна отражать cross-field constraint через discriminated `oneOf`/equivalent + runtime validation.

Description объясняет разницу на русском.

Server не переводит direct request в Job автоматически из-за размера/времени.

---

## 26. MCP `content_parse`

Аналогично:

```text
execution=direct
→ existing request-bound content_ids limit
→ direct result

execution=durable
→ content_ids 1..256
→ JobRef
```

No parser ID argument.

---

## 27. Job tools

Lifecycle tools:

```text
job_get
job_cancel
```

`job_get`:

- owner-scoped;
- job state;
- progress;
- current attempt/retry summary in agent-friendly bounded form;
- result manifest ContentRef when available;
- errors/hints.

`job_cancel`:

- idempotent cancellation request;
- returns current cancellation state;
- does not claim instant cancellation if worker still running.

No generic `job_run(command,args)`.

---

## 28. REST facade

REST can expose richer explicit durable creation endpoints, e.g.:

```text
POST /api/v1/jobs/retrieval-batches
POST /api/v1/jobs/content-parse-batches
GET  /api/v1/jobs/{job_id}
POST /api/v1/jobs/{job_id}/cancel
GET  /api/v1/jobs/{job_id}/events
```

Это нормально: REST является полным programmatic facade и не обязан копировать компактную MCP grouping.

Routes всё равно вызывают typed application services/job registry, а не arq напрямую.

---

## 29. Why no generic public Job create

Generic body:

```json
{"type":"anything","arguments":{}}
```

плохо подходит:

- MCP schema растёт union-ом всех workloads;
- authorization/budgets менее очевидны;
- легко превратить runtime в arbitrary executor;
- REST OpenAPI хуже выражает typed contracts.

Internal Job framework generic; public creation typed.

---

## 30. Crawl deferral

Crawl requires separate design covering at least:

- allowed starting origins/scopes;
- robots policy;
- sitemap handling;
- frontier ordering;
- URL normalization/dedup;
- depth/page/domain limits;
- loops/traps;
- rate politeness;
- duplicate content;
- dynamic Browser relationship;
- result graph/manifest.

Поэтому `crawl` не реализуется как «retrieval_batch с найденными ссылками» в v0.6.

---

## 31. Tests

Required:

1. retrieval 256-item durable creation;
2. content parse durable creation;
3. input order preserved;
4. worker crash after N succeeded → retry skips succeeded;
5. running items recovered after lost attempt;
6. stale attempt cannot commit item;
7. per-item permanent failure + overall partial success;
8. retryable item failure succeeds later;
9. representation reuse after retry;
10. cancellation prevents new items;
11. partial cancellation manifest;
12. aggregate resource budget exhaustion;
13. manifest creation crash/recovery;
14. MCP direct/durable `oneOf` schema positive/negative cases;
15. no auto direct→durable switch;
16. job_get/cancel ownership;
17. no generic arbitrary job type public surface.

---

## 32. Consequences

Плюсы:

- real resumable batch jobs;
- honest measurable progress;
- successful items not repeated after crash;
- same Search/Retrieval/Content application logic reused;
- MCP tool catalog remains compact;
- REST remains powerful/typed;
- crawl complexity not smuggled into generic Jobs.

Минусы:

- additional JobItem table/state machine;
- batch result manifest lifecycle;
- more reconciliation logic;
- MCP existing tool results become execution-mode union.

Trade-off принимается ради production-grade durable semantics rather than superficial async wrapping.

---

## 33. Не определяется

- future distributed item sharding across workers;
- crawl;
- durable Browser workflows;
- maintenance jobs public exposure;
- exact JobItem table column names;
- exact request-bound `content_parse` MCP max count (version implementation must preserve existing v0.3 schema unless intentionally revised);
- future generic internal operator job API.

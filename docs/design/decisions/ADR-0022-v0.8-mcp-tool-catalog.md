# ADR-0022 — v0.8 MCP semantic catalog boundary

**Статус:** superseded in part by ADR-0024 and ADR-0025

## 1. Сохраняемое решение

Главный accepted invariant:

```text
one tool
→ one primary semantic intent
→ one stable execution/lifecycle class
```

MCP не является зеркалом REST/Playwright/provider API.

Semantically coherent batch внутри одного intent допустим, но discriminator не должен смешивать fundamentally different lifecycle/retry classes.

---

## 2. Решения, которые остаются принятыми

### Direct vs durable разделены

```text
web_fetch
web_fetch_job

content_parse
content_parse_job
```

Не используется:

```text
execution = direct | durable
```

потому что direct operation и Job resource creation имеют разные retry/lifecycle semantics.

Деталь закреплена ADR-0021.

### Browser tabs read-only

```text
browser_tabs
```

только читает список Pages.

Создание/закрытие Pages отдельны:

```text
browser_page_create
browser_page_close
```

Нет обязательного hidden `active page`; Browser actions получают explicit `page_id`.

### Form controls объединены по intent

`browser_fill_form` покрывает обычную установку значений text/select/checkbox/radio controls как один последовательный semantic form-fill.

Нет baseline aliases:

```text
browser_select
browser_check
```

Form fill не submit автоматически.

### No raw/browser/admin primitives

Core MCP не содержит:

- arbitrary Job runner;
- policy/admin/worker controls;
- provider credential controls;
- raw HTTP request proxy;
- CSS/XPath targeting;
- arbitrary JavaScript evaluate;
- shell/Python;
- local server filesystem path.

---

## 3. Что уточнил ADR-0024

Первоначальная формулировка ADR-0022 слишком широко называла некоторые read-oriented operations `safe`.

ADR-0024 установил более точное правило:

> retry/annotation class учитывает не только mutation target website, но также billable upstream cost и создание Web Access resources.

В частности:

- `web_search` не blind-auto-retry после возможного billable provider dispatch;
- `web_fetch` создаёт Content resources и не является безусловно safe/idempotent replay;
- `content_parse` может считаться idempotent только после доказанного canonical representation reuse.

При конфликте retry wording этого исторического ADR с ADR-0024 приоритет имеет ADR-0024 и exact `contracts/mcp-tools.md`.

---

## 4. Что добавил ADR-0025

Первоначальный catalog не имел explicit scroll capability.

ADR-0025 доказал, что bounded snapshot без scroll оставляет functional gap для:

- длинных страниц;
- lazy/infinite content;
- scrollable containers;
- interactive elements вне текущего bounded ref inventory.

Поэтому добавлен:

```text
browser_scroll
```

и freeze candidate теперь содержит **28 tools**, а не 27.

Scroll explicit, viewport-relative, не скрывается внутри snapshot.

---

## 5. Актуальный catalog source

Точный current catalog, fields, bounds, result shapes и execution metadata больше **не дублируются** в этом ADR.

Канонические владельцы:

```text
semantic facade
→ ../mcp.md

exact DTO/catalog
→ ../contracts/mcp-tools.md
```

Это предотвращает рассинхронизацию ADR и schema contract при дальнейших design refinements до freeze.

---

## 6. Batch rule

Batch используется только когда элементы являются независимыми экземплярами одной операции или одним цельным semantic compound action:

```text
queries[]
urls[]
content IDs[]
session cleanup[]
job read/cancel IDs[]
form fields[]
```

Sequential Browser state transitions не сворачиваются в giant action batch.

No `*_many` aliases.

---

## 7. Compatibility

Catalog является **v0.8 freeze candidate**, а не уже опубликованным v1 runtime contract.

До v0.8 actual schema freeze допустимы только explicit reviewed design refinements вроде ADR-0024/0025.

После v0.8:

- removal/rename/meaning change → compatibility review;
- additive tool → отдельный semantic intent/execution review;
- generated FastMCP fixture diff → CI-visible;
- own-agent trusted descriptor update required where semantics change.

---

## 8. Consequences

Плюсы:

- trusted Agent Dispatcher metadata остаётся per-tool;
- LLM не угадывает argument-sensitive lifecycle;
- direct/durable resources explicit;
- Browser state transitions наблюдаемы;
- tool catalog остаётся semantic, а не библиотечным.

Минусы:

- core catalog не минимален по количеству names;
- facade design требует отдельной contract-review discipline.

Это сознательный trade-off: **меньше неоднозначности важнее минимального числа tools**.

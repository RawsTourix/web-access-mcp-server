# ADR-0022 — v0.8 MCP freeze candidate: explicit lifecycle, one stable execution class per tool

**Статус:** accepted

## 1. Контекст

До v0.8 MCP design содержал несколько exploratory decisions:

- mixed `browser_tabs` list/new/select/close command;
- direct/durable discriminator внутри `web_fetch/content_parse`;
- optional standalone select/check browser tools;
- approximate Browser catalog.

Для собственного Agent Dispatcher и generic MCP clients tool identity должна устойчиво означать одну semantic operation class.

Особенно важны:

- retry class;
- side-effect/resource behavior;
- result type;
- lifecycle ownership;
- progress presentation.

---

## 2. Главный принцип freeze

```text
one tool
→ one primary intent
→ one stable execution/lifecycle class
```

Это не означает «одна кнопка = один tool» любой ценой.

Semantically coherent batch внутри операции допустим (`queries[]`, `urls[]`, form fields), но discriminator не должен превращать read-only tool в resource-creating/mutating tool с другим retry contract.

---

### Content

## 4. `web_search`

Intent:

> Найти подходящие URL/источники по одному или нескольким независимым поисковым запросам.

Batch:

```text
queries[]
```

Search snippets are not page content.

Execution class:

```text
request-bound
safe/read-oriented
```

No page fetch.

---

## 5. `web_fetch`

Intent:

> Немедленно получить один или несколько известных URL обычным безопасным HTTP(S) Retrieval и выполнить доступные L0/L1 Content operations.

```text
urls 1..8 baseline
```

No Browser/L2/Job.

Execution:

```text
request-bound
safe/read-oriented
```

---

## 6. `web_fetch_job`

Intent:

> Создать durable Job для большого batch известных URL.

```text
urls 1..256 MCP baseline
→ JobRef
```

Execution:

```text
creates durable resource
never blind automatic retry after uncertain creation outcome
```

No auto-switch from `web_fetch`.

---

## 7. `content_get`

Intent:

> Прочитать существующие ContentObjects/representations bounded chunks без acquisition/parsing side effect.

Batch:

```text
items[] content_id + cursor
```

Read-only/safe.

---

## 8. `content_parse`

Intent:

> Немедленно выполнить доступный L1 Native Parsing для существующих ContentObjects.

```text
content_ids 1..8 freeze baseline
```

Server chooses canonical registered parser. No parser library ID.

Safe/idempotent representation-producing operation relative immutable source/provenance reuse.

No L2/Job.

---

## 9. `content_parse_job`

Intent:

> Создать durable Content Native Parsing batch Job.

```text
content_ids 1..256
→ JobRef
```

Resource-creating; never blind auto retry after uncertain Job creation.

---

## 10. `browser_create`

Creates exactly one ephemeral BrowserSession + initial blank page.

No URL input.

Resource-creating.

Result:

```text
browser_session_id
initial page_id
lifetime metadata
```

---

## 11. `browser_get`

Read current owner-authorized BrowserSession metadata/state/lifetime.

Read-only/safe.

Useful for lifecycle recovery without taking snapshot/page action.

---

## 12. `browser_close`

Idempotent cleanup.

Batch of session IDs allowed because cleanup operations are independent and share same semantics:

```text
session_ids[]
```

Per-session result distinguishes:

```text
closed
already_terminal
lost/not_found/forbidden etc.
```

---

## 13. `browser_navigate`

One navigation intent with destination discriminator:

```text
url
back
forward
reload
```

All variants mutate browser/page state and share never-blind-retry semantics.

`page_id` explicit.

No create/new tab.

---

## 14. `browser_snapshot`

Read interactive semantic page state + `element_ref` inventory.

Read-only observation.

No screenshot auto attachment.

---

## 15. `browser_content`

Read rendered current page as document-like Content representation through Content boundary.

Distinct from snapshot:

```text
snapshot → interaction targeting
content  → document reading/analysis
```

It may create ContentObject internally but does not perform website mutation; execution metadata may classify it as safe representation-producing operation.

---

## 16. `browser_tabs`

**Read-only list/inspect only.**

Returns pages/tabs with IDs, URL/title/state metadata.

Removed mixed commands:

```text
new
select
close
```

There is no required hidden `active page` concept in MCP. Every page operation receives explicit `page_id`.

---

## 17. `browser_page_create`

Creates one new blank Page inside existing BrowserSession.

Returns new `page_id`.

No URL navigation hidden.

Mutating internal resource; never blind retry because duplicate page creation is possible after uncertain response.

---

## 18. `browser_page_close`

Closes explicit page.

Idempotent where possible (`already_closed/not_found` normalized).

Baseline invariant: service must not silently create replacement page. If implementation requires at least one page, closing final page is rejected `last_page_close_rejected`; otherwise zero-page session semantics must be explicit. Freeze baseline chooses **reject closing the last page**, preserving one-live-page invariant.

---

## 19. `browser_screenshot`

Explicit screenshot to ContentObject.

Input:

```text
session_id
page_id
optional element_ref
bounded approved capture options
```

No inline base64 large result.

Safe representation-producing class; potential duplicate Content output handled through content lifecycle/quota, not external website side effect.

---

## 20. `browser_events`

Read-only bounded diagnostic event stream.

Filters:

```text
types[]
page_id | null
after_sequence | null
limit
```

Combines console/network/page/dialog/download/security events because underlying intent is one bounded event log read.

---

## 21. `browser_click`

Explicit `element_ref` click.

Potential external side effect.

Never blind auto retry after uncertain dispatch.

---

## 22. `browser_fill_form`

Batch fields belonging to one semantic form-fill operation:

```text
fields[]:
  element_ref
  typed value
```

Supports ordinary form control classes:

- text value;
- select option/value;
- checkbox/radio checked state where snapshot identifies control.

Does **not** submit automatically.

This removes need for separate `browser_select`/`browser_check` MCP tools baseline.

Per-field result preserves partial mutation.

---

## 23. `browser_type`

Incremental/eventful text input distinct from setting a form value.

Target `element_ref` + text.

Potentially side-effecting page state; never blind retry.

---

## 24. `browser_press`

Keyboard key/shortcut action.

Optional target only if application contract safely supports page-level keyboard.

Never blind retry because Enter/shortcut can submit/navigate.

---

## 25. `browser_hover`

Explicit hover intent for menus/tooltips/lazy UI state.

Target `element_ref`.

State-mutating/open-world; conservative retry class.

---

## 26. `browser_drag`

Explicit drag-and-drop:

```text
source_element_ref
target_element_ref
```

No arbitrary screen coordinates baseline.

Never blind retry.

---

## 27. `browser_wait`

Wait for explicit bounded condition.

Typed variants baseline candidates:

```text
duration
URL condition
element state via element_ref
page load state
```

No free-form Python/JS predicate.

Read/observation-oriented but open-world time progression; server never claims whole website «finished» semantically.

---

## 28. `browser_upload`

Attach owner-authorized ContentObject to explicit file input `element_ref`.

No host path.

Potentially side-effecting; never blind retry after uncertain dispatch.

---

## 29. Downloads

No dedicated `browser_download` baseline.

A download is artifact/event caused by explicit action/navigation.

Saved through Content boundary and returned as ContentRef.

Direct downloadable URL uses `web_fetch` where possible.

---

## 30. `job_get`

Read-only batch Job status:

```text
job_ids[]
```

Returns state/progress/result manifest ref/errors/hints.

---

## 31. `job_cancel`

Idempotent batch cancellation request:

```text
job_ids[]
```

Response may be `cancelling`, not fake immediate `cancelled`.

---

## 32. No generic/admin tools

Not in normal MCP:

```text
job_create arbitrary
provider_list/admin
worker status/drain
policy update
parser registry
raw HTTP request
browser evaluate
CSS/XPath action
shell/Python
```

REST/operator surface owns those appropriate programming/administrative capabilities.

---

## 33. Tool-level execution metadata invariant

Each frozen tool must map to one stable trusted Agent execution descriptor.

A field discriminator may change variants **only if variants share same retry/side-effect/resource class**.

Examples allowed:

```text
browser_navigate: url/back/forward/reload
```

Examples forbidden:

```text
browser_tabs: list OR create OR close
web_fetch: direct OR create Job
```

---

## 34. Batch rule

Batch is used when multiple items are independent instances of the same operation:

```text
queries[]
urls[]
content read items[]
browser_close session_ids[]
job_get/job_cancel job_ids[]
form fields[] as one semantic form-fill
```

No `*_many` aliases.

Sequential state transitions remain separate calls.

---

## 35. Descriptions

All tool/field descriptions Russian.

Tool description structure:

1. what it does;
2. when to use / neighbor difference;
3. critical limitation/side-effect if relevant.

Do not dump implementation details.

---

## 36. Schema tests

For every frozen tool actual FastMCP schema tests verify:

- every public field/nested field description;
- required/default/null semantics;
- min/max/list bounds;
- enum/discriminator;
- unknown fields rejected;
- no infrastructure/private fields;
- tool annotations;
- stable result kind.

---

## 37. Agent integration

Trusted descriptors can now remain per-tool, without argument-sensitive execution classification.

Especially:

```text
web_fetch safe
web_fetch_job resource_create/never_blind_retry
content_parse safe/idempotent
content_parse_job resource_create/never_blind_retry
browser_tabs safe
browser_page_create mutating
browser_page_close idempotent cleanup-like page mutation
```

This simplifies ToolDispatcher and presentation profiles.

---

## 38. Compatibility

This catalog is v0.8 freeze candidate.

Before v1.0, removal/rename requires explicit compatibility review.

Future additive tool requires real new intent and must not duplicate existing operation for convenience.

---

## 39. Consequences

Плюсы:

- precise trusted metadata;
- cleaner agent reasoning;
- no mixed read/write tool;
- no active-page hidden state;
- form actions compact without select/check proliferation;
- durable lifecycle explicit;
- catalog powerful but still far smaller than raw Playwright surface.

Минусы:

- page create/close add two tools;
- direct/durable adds two Job-creation tools;
- 27 tools total baseline is non-trivial and requires good descriptions/discovery.

Catalog size accepted because each remaining tool represents a real semantic operation rather than API-library method explosion.

---

## 40. Не определяется

- future visual/VLM browser tool;
- advanced JavaScript/locator admin capability;
- persistent browser profiles;
- native MCP Tasks projection;
- future crawl tool.
